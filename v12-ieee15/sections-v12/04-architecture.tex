\section{System Architecture}\label{sec:impl}

\sys{} is not a separate service: the cascade, its labels and the issue states run inside the review composition of a capstone review portal used by faculty supervisors and student teams (deployment diagram in the extended report). Caddy serves the client and proxies a FastAPI application that owns authentication, authorization on every protected route, validation and all durable state. Celery workers on a Redis queue analyse submissions (rule checks, a language-model review and a partner claim-to-code tracer, whose results arrive as signed bundles) and compose reviews. PostgreSQL holds versions, issues, anchors, revisions and a change journal; archives and media notes are kept in a store addressed by SHA-256 digest.

\textbf{Data and composition.} Report versions form a chain, and each has one review document holding the supervisor's issues, each with a status, severity, category, title, body and up to twelve anchors. A carried issue's origin reference, \texttt{carry:v$t$:id}, records its lineage and makes composition idempotent; every edit appends an attributed revision and must name the revision it was based on, so concurrent edits are detected rather than lost. Composition locks the version's row, because several clients may compose it at once, and runs carry-forward before the new analysis, so that a finding raised again is matched to the issue the supervisor already has. The review page shows a banner (``$N$ points carried over $\cdot$ $M$ need a re-check''), a ``From version~$n$'' tag on each carried issue and a plain-language note on each anchor. An optional assistant edits review points only through journaled, undoable tool calls, and a resolve or dismiss it suggests takes effect only when a supervisor applies it. The evaluated functions come from a pinned source snapshot identified in the artifact; the guards and the identity rule were evaluated over that snapshot and are not yet part of the deployed composition.
