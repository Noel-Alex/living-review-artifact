\section{RQ3: The Implemented State Contract}\label{sec:statecheck}
The safety argument rests on rules about who may change an issue's state. We checked them against the pinned application in three ways.

\textbf{Specification.} The extended report tabulates the implemented transitions (\wpdTransitionRows{} rows) with actor, source and target state and the source lines that implement each, checked when the table is generated; a last row records that no code path lets the system write \lbl{resolved}. Faculty status edits have no source-state guard: a supervisor may set any state from any state.

\textbf{Static scan and bounded model.} A scan of the abstract syntax trees found \wpdWriters{} call sites that create, update, delete, restore or undo a review issue, and no direct assignment to its status; none of the system writers writes \lbl{resolved}, so the headline property rests on the scan. A bounded model of the transitions for two findings and two versions, with every carried issue's relocation label chosen nondeterministically, visited \wpdStates{} states and \wpdTransitions{} transitions to depth \wpdDepth. No system event wrote \lbl{resolved} (\wpdSystemResolved{} violations), revision history stayed append-only, repeated composition changed nothing, and the assistant never closed an issue without a supervisor's confirmation. One invariant failed: an active issue was not carried to the next version on \wpdNotCarried{} transitions, all through deletion (\wpdNotCarriedFaculty{} by a supervisor, \wpdNotCarriedAgent{} by the assistant). Deletion is journaled and undoable, but a deleted issue is not carried forward, so the verified property is narrow: no system event resolves an issue, which does not mean that no concern leaves the workflow.

\textbf{Scenarios against the application.} Of the pinned application's own review-state and artifact tests, \wpdAppTestsPassed{} of \wpdAppTestsCollected{} passed, \wpdAppTestsFailed{} failed and \wpdAppTestsSkipped{} was skipped, none for reasons of review state. We then wrote \wpdScenarioRun{} scenarios that submit versions, import signed analysis bundles and compose reviews through the application's interfaces. Five claims held: a three-version chain was labeled moved, changed and removed in turn with its lineage kept; a change to one supporting anchor returned a multi-anchor issue; repeated composition was idempotent, and on PostgreSQL~\wpdPgVersion{} concurrent composers produced no duplicates; media notes followed their issue or code. Three did not, and the design text was corrected: dismissal memory compares only with the preceding version by a heuristic key, so a different finding with the same opening paragraph was suppressed and a finding absent for one version arrived \lbl{open}; carry-forward reads only the preceding version's review, so an uncomposed version blocks carry until it is composed; and an unchanged file above the carry size limit had its anchor labeled \lbl{removed}, a false re-check rather than a silent error.

\textbf{A stronger contract.} Table~\ref{tab:contract} lists each gap, the implemented behavior and a proposed rule. Its invariants refine S4 and S5: no system write of \lbl{resolved} (S4a) or \lbl{dismissed} (S4b), no assistant closing or withdrawal without a supervisor (S4c), and withdrawn issues visible later (S5-vis). A supervisor's withdrawal leaves a visible tombstone that later versions carry, and the assistant may only propose one; undo recomposes the versions composed after the withdrawal; dismissal identity combines category, normalized title and a digest of the reviewed quotations and is compared with every earlier version; a finding that matches a dismissal is created \lbl{open} with a note naming the dismissal, so the system never writes \lbl{dismissed}; and a version composed late recomposes its descendants. A bounded model over two findings with colliding keys, three versions and all sixteen label assignments of two anchors, covering every ordering of each gap's events to depth \wcDepth{} (\wcStatesImpl{} and \wcStatesStrong{} distinct states), reproduced every gap in the implemented contract, each with a minimal event trace, and found none in the proposed one. The proposed contract is specified and model-checked, not implemented.

\textbf{Answer to RQ3.} No system event resolves an issue, by construction of the code. The stronger property a course would want, S4 and S5 together, does not hold in the implementation: deletion by a supervisor or the assistant and an uncomposed version stop an issue from being carried, and dismissal memory creates a different finding already \lbl{dismissed}, a system closing. The proposed contract closes these gaps in the model; the portal still needs it.
